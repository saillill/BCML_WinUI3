**路径合规性校验规则**（与 `Api.dir_exists` 完全一致）：

| 类型 | 判定依据 |
|---|---|
| 本体目录 | 存在 `Pack/Dungeon000.pack` |
| 更新数据目录 | `Actor/Pack` 下 `*.sbactorpack` 数量 > 7000 |
| DLC 目录 | 存在 `Pack/AocMainField.pack` |
| Cemu 目录 | 存在 `?emu*.exe` |
| 导出目录 / 数据目录 | 只要求是目录 |

每条路径还提供**「自动定位」**——对应原版的 `drill_dir`：在所填目录及其子目录里搜索特征文件，
自动修正到真正的根目录（选错层级时很实用）。校验结果以 ✓/✗ 标记显示。

**明确省略的原版项**：
- `parse_cemu_settings`（从 Cemu 的 settings.xml 反推游戏路径）——本应用以 Switch/Ryujinx 为主，
  该项仅在 Wii U 模式且已装 Cemu 时才有意义，暂未接入。
- 原版的部分字段（`load_reverse` / `site_meta` / `auto_gb` / `show_gb` / `dark_theme`）
  属于 pywebview 前端的内部开关：`dark_theme` 由本应用的**主题**设置取代，
  其余几项在本架构下无保存必要，保存时原样回写、不做编辑入口。

**已下线项**：
- `nsfw` —— 上游仅在 `bcml/util.py` 的默认值表里声明（全仓库唯一出现处），
  JS 端只有一处同名 state 默认值，`_api.py` 与合并流程**都不读它**，也没有对应界面控件。
  换言之它是**死键**。本应用此前把它当作「允许 NSFW 模组」开关呈现，属误读；
  现已从设置页移除、删除中英词条，并在 `BcmlService.SaveSettingsAsync` 写回前
  `settings.Remove("nsfw")`，避免它被读回来后又被原样存回去。

|---|---|---|

| **Upgrade Old BNP** | ✅ | `sys.upgradeBnp` —— 解包时自动把旧 `rules.txt` 转成 `info.json` 再打包 |
| **Generate RSTB for Mod** | ✅ | `sys.genRstb` —— 只开 rstb 合并器跑一次合并，把 ResourceSizeTable 写回模组 |
| **BNP to Standalone** | ✅ | `sys.bnpToStandalone` —— 独立合并后 `install.export(standalone=True)` |
| **Compare Mods** | ✅ | `sys.compareMods` —— 按合并器分组做左右差集，界面并排渲染 |
| View Merged Files | ✅ | 打开合并输出目录 |

**为什么要补后端接口**：原版这些方法（`create_bnp` / `convert_bnp` / `bnp_to_gfx` /
`upgrade_bnp` / `gen_rstb`）内部都用 `self.window.create_file_dialog` 选路径，
在无界面 sidecar 里会直接返回 `-32010`。做法是让界面先选好路径，再调用后端只负责干活的新接口
（`sys.convertBnp` 就是这个模式，本次其余工具照此办理）。

**BNP Creator 的表单设计**：选项组用一行紧凑写法「组名=值1,值2,值3」+ 复选/单选下拉，
写回 `meta.options`（每个选项值对应 `options/` 下的一个子目录）与 `options.groups`。
单选组安装时默认预选第一个候选值——与原版「作者用 `*` 标注推荐项」的效果一致。

**踩过的坑**：`BcmlMod.from_json` 收的是**字典**（要有 `"path"` 键），不是路径字符串。
最初直接把路径传进去，报 `string indices must be integers`；改为 `from_json({"path": p})` 后正常。

### 备份与「导入/导出」是否重叠？（用户提问）

**不重叠，是两个不同维度，但确实需要说清区别：**

| | 备份（侧栏「备份」） | 导入 / 导出（模组页弹窗） |
|---|---|---|
| 保存内容 | **整个 `mods_nx` 目录的打包**（含所有 mod 文件本体） | **只有清单元数据**：排序、启用状态、合并器选项、已启用的选项目录 |
| 体积 | 数百 MB（随 mod 数量增长） | 通常几 KB |
| 能否还原 mod 文件 | ✅ 能 | ❌ 不能（只还原排序与状态） |
| 能否还原「选项目录」的勾选 | ✅ 能（文件级还原） | ⚠ 只能报告差异，需重装该 mod |
| 典型用途 | 整包迁移 / 出问题前兜底 | 频繁切换「纯净版 / 增强版」的排序与开关 |

一句话：**备份是「连家具一起搬」，导入导出是「只抄一张布置图」。**
两者互补，同时保留；界面上已按此区分措辞。

## 7. 「显示已禁用的模组」是什么意思？（用户提问）

BCML 里每个已安装 mod 可以处于**启用**或**禁用**状态。禁用的实现是在该 mod 目录下放一个
`.disabled` 空文件；合并时 BCML 会**跳过**它们，等效于「装了但暂时不生效」。

- **勾选**（默认）：列表里**包含**已禁用的 mod，它们排在自己的优先级位置上，
  便于随时切回启用。
- **取消勾选**：只显示会**实际生效**的 mod，列表更短，专注当前合并结果。

界面上的措辞已改为「显示已禁用的模组」，并补了悬停说明。

### 8.1 模组详情面板（本轮细化）

原版详情页是一个纵向卡片流。本应用保留这个结构，并按「信息密度」重排为：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 封面 | 大图 + 禁用遮罩 | `api.get_mod_info` 的 base64 缩略图 |
| 标题 + 徽标行 | 启用/禁用、版本、平台、处理状态 | `sys.modDetails` → `meta` |
| 模组信息表 | 优先级 / 文件夹 / 平台 / 版本 / 更新时间 / 模组 ID（只列有值的字段） | 同上 |
| 前置依赖 | `info.json` 的 `depends` | 同上 |
| 已启用选项 | 目录下真实存在的 `options/*` | 同上 |
| 已关闭的合并器 | `options.json` 的 `disable` | 同上 |
| 内容描述 | Markdown 渲染 | `api.get_mod_info` 的 `desc` |
| 涉及改动 | 该模组涉及的合并器名 | `api.get_mod_info` 的 `changes` |
| **改动明细** | 按合并器分组的**文件清单**，逐组折叠、等宽字体、超 300 项截断 | **`sys.modDetails` → `edits`**（新增） |
| 可用操作 | 文件夹 / 来源页 / 启用停用 / 更新 / 上移 / 下移 / 重新处理 / 卸载 | — |

设计要点：

- **一次 RPC 拿全**元数据 + 选项目录 + 改动清单（`sys.modDetails`）。分三次调用会让界面
  出现三次「转圈」，合成一次后只有一个加载态。
- **懒加载 + 按目录缓存**：改动清单要遍历模组文件（实测最大的模组 1386 个文件 / 9 个合并器），
  所以只在**选中某个模组时**才请求一次；在列表里来回点不会重复请求，列表刷新时缓存整体失效。
- **单个合并器报错不影响整体**：某个合并器 `get_mod_edit_info` 抛异常时按空处理，
  原因写进日志环（「日志」页可见）。
- 原版 `Api.get_mod_edits` 只返回文件清单、不返回元数据；本应用的 `sys.modDetails`
  在它基础上合并了 `info.json` 元数据与选项目录，并把排序改成「文件多的组排前面」。
