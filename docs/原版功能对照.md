**Path validation rules** (identical to `Api.dir_exists`):

| Kind | Criterion |
|---|---|
| Base game directory | `Pack/Dungeon000.pack` exists |
| Update directory | more than 7000 `*.sbactorpack` files under `Actor/Pack` |
| DLC directory | `Pack/AocMainField.pack` exists |
| Cemu directory | `?emu*.exe` exists |
| Export / data directory | only needs to be a directory |

Every path field also offers **Auto-locate**, the equivalent of upstream's `drill_dir`:
it searches the given directory and its subdirectories for a signature file and corrects
the path to the real root, which is useful when the wrong folder level was selected.
Validation results are shown with ✓/✗ marks.

**Upstream items deliberately omitted**:

- `parse_cemu_settings` (deriving the game path from Cemu's `settings.xml`) — this app
  targets Switch / Ryujinx first, and that item only matters in Wii U mode with Cemu
  installed.
- Several upstream fields (`load_reverse` / `site_meta` / `auto_gb` / `show_gb` /
  `dark_theme`) are internal switches of the pywebview front end. `dark_theme` is
  replaced by this app's **theme** setting; the rest need no persistence in this
  architecture — they are written back unchanged and expose no editing control.

**Wizard implementation notes**

- Shares the same path validation (`Api.dir_exists`) and save endpoint
  (`save_settings`) with the settings page; the rules are not implemented twice.
- "Save and continue" stays disabled until every required path validates — the same bar
  as the upstream FirstRun.
- On completion `wizardDone` is written to `app.json` and the wizard stops appearing
  automatically; it can also be skipped from within the wizard.
- For debugging, `--wizard 1..4` jumps straight to a given page (independent of
  `wizardDone`), which is convenient for screenshots and smoke tests.

**About the busy messages**: upstream states plainly that "real progress updates are not
an option" — the BCML backend does not report real progress. This app therefore also
shows only a spinner plus a message, and never fabricates a percentage. All 95 messages
are kept verbatim (the game references and official tips lose their flavour in
translation); the Chinese UI shows translations alongside the earlier game references.

## 5. Tools Page (`DevTools.jsx`)

**Every upstream DevTools utility is wired up** (through the six headless sidecar
endpoints):

| Upstream tool | Status | Sidecar endpoint |
|---|---|---|
| **BNP Creator** | ✅ | `sys.createBnp` — full form: folder / name / version / author / icon / dependencies / option groups (checkbox and radio) |
| **Convert BNP Platform** (Switch ↔ Wii U) | ✅ | `sys.convertBnp` — supports both "skip and list warnings" and "abort" strategies |
| **Upgrade Old BNP** | ✅ | `sys.upgradeBnp` — converts a legacy `rules.txt` into `info.json` during unpacking, then repacks |
| **Generate RSTB for Mod** | ✅ | `sys.genRstb` — runs one merge with only the rstb merger enabled and writes the ResourceSizeTable back into the mod |
| **BNP to Standalone** | ✅ | `sys.bnpToStandalone` — merges standalone, then `install.export(standalone=True)` |
| **Compare Mods** | ✅ | `sys.compareMods` — per-merger left/right set difference, rendered side by side |
| View Merged Files | ✅ | Opens the merged output directory |

**Why extra backend endpoints were needed**: upstream these methods (`create_bnp` /
`convert_bnp` / `bnp_to_gfx` / `upgrade_bnp` / `gen_rstb`) all use
`self.window.create_file_dialog` to pick a path, which returns `-32010` in a headless
sidecar. The approach is to let the UI pick the path first and then call a new endpoint
that only does the work (`sys.convertBnp` follows this pattern, and the remaining tools
do the same).

**BNP Creator form design**: option groups use a compact one-line form
`group=value1,value2,value3` plus checkbox / radio selectors, written back to
`meta.options` (each option value maps to a subdirectory under `options/`) and
`options.groups`. A radio group pre-selects its first candidate on install, matching the
effect of upstream's convention of marking the recommended item with `*`.

### Backups vs. import/export

These are two different things and are complementary; both are kept, and the UI wording
distinguishes them.

| | Backup (sidebar → Backups) | Import / export (mods page dialog) |
|---|---|---|
| What is stored | **A packed copy of the whole `mods_nx` directory** (including all mod files) | **Only list metadata**: order, enabled state, merger options, enabled option folders |
| Size | hundreds of MB (grows with the mod count) | usually a few KB |
| Restores mod files | ✅ yes | ❌ no (order and state only) |
| Restores option-folder selections | ✅ yes (file-level restore) | ⚠ reports differences only; the mod must be reinstalled |
| Typical use | whole-set migration / a safety net before trouble | frequently switching order and on/off state between different builds |

In short: a **backup moves the furniture with the house**; import/export **copies just the
floor plan**.

## 7. Showing Disabled Mods

Every installed mod in BCML is either **enabled** or **disabled**. Disabling is
implemented by placing an empty `.disabled` file in the mod's directory; BCML **skips**
those mods when merging, which is equivalent to "installed but temporarily inactive".

- **Checked** (default): the list **includes** disabled mods, each at its own priority
  position, so they can be switched back on at any time.
- **Unchecked**: only mods that **actually take effect** are listed, giving a shorter
  list focused on the current merge result.

The label in the UI is "Show disabled mods" and a tooltip explains it.

### 8.1 Mod Details Panel

Upstream's details page is a vertical card flow. This app keeps that structure and
rearranges it by information density:

| Section | Content | Source |
|---|---|---|
| Cover | Large image plus a disabled overlay | base64 thumbnail from `api.get_mod_info` |
| Title + badge row | Enabled/disabled, version, platform, processing state | `sys.modDetails` → `meta` |
| Mod info table | Priority / folder / platform / version / update time / mod ID (only fields with values are listed) | same |
| Dependencies | `depends` from `info.json` | same |
| Enabled options | `options/*` directories that actually exist on disk | same |
| Disabled mergers | `disable` from `options.json` | same |
| Description | Markdown rendering | `desc` from `api.get_mod_info` |
| Mergers affected | Names of the mergers the mod touches | `changes` from `api.get_mod_info` |
| **Change details** | **File list grouped by merger**, collapsible per group, monospaced, truncated beyond 300 entries | **`sys.modDetails` → `edits`** |
| Available actions | Folder / source page / enable-disable / update / move up / move down / reprocess / uninstall | — |

Design notes:

- **One RPC call returns everything** — metadata, option folders and the change list
  (`sys.modDetails`). Three separate calls would produce three spinner phases; combining
  them leaves a single loading state.
- **Lazy loading with per-directory caching**: building the change list walks the mod's
  files (the largest mod measured 1386 files across 9 mergers), so it is requested only
  when a mod is selected; clicking back and forth in the list does not re-request, and
  the cache is invalidated wholesale when the list refreshes.
- **A single failing merger does not break the rest**: if one merger's
  `get_mod_edit_info` raises, it is treated as empty and the reason is written to the log
  ring (visible on the Logs page).
- Upstream `Api.get_mod_edits` returns only the file list and no metadata; this app's
  `sys.modDetails` merges in the `info.json` metadata and the option folders on top of
  it, and sorts groups with more files first.

## 7. 「显示已禁用的模组」

BCML 里每个已安装 mod 可以处于**启用**或**禁用**状态。禁用的实现是在该 mod 目录下放一个
`.disabled` 空文件；合并时 BCML 会**跳过**它们，等效于「装了但暂时不生效」。

- **勾选**（默认）：列表里**包含**已禁用的 mod，它们排在自己的优先级位置上，
  便于随时切回启用。
- **取消勾选**：只显示会**实际生效**的 mod，列表更短，专注当前合并结果。

界面上的措辞为「显示已禁用的模组」，并配悬停说明。

### 8.1 模组详情面板

原版详情页是一个纵向卡片流。本应用保留这个结构，并按「信息密度」重排为：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 封面 | 大图 + 禁用遮罩 | `api.get_mod_info` 的 base64 缩略图 |
| 标题 + 徽标行 | 启用/禁用、版本、平台、处理状态 | `sys.modDetails` → `meta` |
| 模组信息表 | 优先级 / 文件夹 / 平台 / 版本 / 更新时间 / 模组 ID（只列有值的字段） | 同上 |
| 前置依赖 | `info.json` 的 `depends` | 同上 |
| 已启用选项 | 目录下真实存在的 `options/*` | 同上 |
| 已关闭的合并器 | `options.json` 的 `disable` | 同上 |
| 内容描述 | Markdown 渲染 | `api.get_mod_info` 的 `desc` |
| 涉及改动 | 该模组涉及的合并器名 | `api.get_mod_info` 的 `changes` |
| **改动明细** | 按合并器分组的**文件清单**，逐组折叠、等宽字体、超 300 项截断 | **`sys.modDetails` → `edits`** |
| 可用操作 | 文件夹 / 来源页 / 启用停用 / 更新 / 上移 / 下移 / 重新处理 / 卸载 | — |

设计要点：

- **一次 RPC 拿全**元数据 + 选项目录 + 改动清单（`sys.modDetails`）。分三次调用会让界面
  出现三次「转圈」，合成一次后只有一个加载态。
- **懒加载 + 按目录缓存**：改动清单要遍历模组文件（实测最大的模组 1386 个文件 / 9 个合并器），
  所以只在**选中某个模组时**才请求一次；在列表里来回点不会重复请求，列表刷新时缓存整体失效。
- **单个合并器报错不影响整体**：某个合并器 `get_mod_edit_info` 抛异常时按空处理，
  原因写进日志环（「日志」页可见）。
- 原版 `Api.get_mod_edits` 只返回文件清单、不返回元数据；本应用的 `sys.modDetails`
  在它基础上合并了 `info.json` 元数据与选项目录，并把排序改成「文件多的组排前面」。
